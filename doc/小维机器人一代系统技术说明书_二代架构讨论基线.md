## 0. 一句话总览

机器人端以 **ROS 2 Humble + Horizon TROS** 为核心；业务编排在 **`mapping_service`**；对外控制面不是独立业务协议栈，而是 **Foxglove Bridge WebSocket（8765）+ 静态 Web（9000）**；Android / 平板与网页 **共用同一套话题和服务**；速度统一经 **`laser_safety` → `/cmd_vel` → 底盘串口**；视觉可拆到 **Domain 35 + domain_bridge**；稳定性靠 **软件话题看门狗 + 启动预检**；CPU 控制靠 **白名单、降帧、关推流、少建 DDS、限重试**，而不是 cgroup 硬配额。

## 5. ROS2 负责什么

ROS2 在本项目中是 **机端实时总线 + 功能编排 + 导航/感知节点图**，不是云协议。

| 层次 | ROS2 职责 | 非 ROS2 职责 |
|------|-----------|--------------|
| 驱动 | 雷达/超声/底盘 odom·imu·急停 | 前端 UI、OTA MQTT 契约 |
| 安全 | laser_safety 合并速度、急停话题 | 法律合规级安全认证（无） |
| 业务门闸 | mapping_service 服务启停各模式 | 直接在 JS 里 spawn 进程（除少数 nohup 实现细节） |
| 导航 | Nav2 action、AMCL/tf、路径 | 安卓原生路径规划 |
| 状态外发 | topic 状态码、终态、电量 | 推送通知系统（需安卓另做） |
| 对外桥 | foxglove_bridge 序列化子集话题 | 全量 DDS 暴露（刻意不做） |
| 视觉隔离 | domain 35 + bridge 最小集 | 主域里常开高帧 AI（默认避免） |

**`mapping_service` 是唯一业务总闸**：Web/安卓应通过其 service 开关建图/导航/跟随等，而不是各客户端各自 `ros2 launch`（后台脚本是运维例外）。

### 6.1 端口表

### 6.2 WebSocket 到底是什么

- **传输**：标准 WebSocket（TCP 上的全双工）。
- **应用协议**：**Foxglove WebSocket 协议**，不是 roslibjs 原生 rosbridge JSON 协议。
- **前端适配**：`roslib_foxglove.js` 提供 **ROSLIB 兼容 shim**，页面仍写 `ROSLIB.Ros / Topic / Service`，底层走 Foxglove。
- **加载顺序**（必须）：`foxglove_bundle.js` → `ros2_schemas.js` → `roslib_foxglove.js` → `ros_ws_helper.js`。
- **默认地址**：`ws://<机器人IP>:8765`。

迁移文档：`src/mapping_service/FOXGLOVE_MIGRATION.md`。

### 6.3 foxglove_bridge 是什么（不是 “foxbridge” 独立产品）

`foxglove_bridge` 是跑在机器人上的 ROS 节点，职责：

1. 把 **白名单内** 的 ROS topic 序列化推给所有已订阅的 WS 客户端；  
2. 把客户端发布的 topic（`client_topic_whitelist`）注入 ROS；  
3. 代理 **service_whitelist** 内的服务调用并回传 response；  
4. 用 `max_update_ms`、depth 限制、关闭 compression 等控制带宽/CPU。

**关键设计（CPU 友好）**：不全网镜像话题。白名单在 `mapping_service_web.launch.py`。

## 7. 和安卓怎么通讯

仓库内 **无独立 Android 原生 SDK 源码**；平板/安卓约定为：

1. **WebView 或浏览器** 打开 `http://<机器人>:9000/...`；或  
2. **原生客户端直接实现 Foxglove WS**，订阅/发布同一话题、调用同一服务。

已有联调文档：

- `mapping_service/docs/Android定位状态联调.md` — `/localization_status`
- `mapping_service/docs/Android充电类型状态联调.md` — 充电类型
- `sound_source_navigation/docs/Android联调清单.md`
- `web/CURSOR_导航页朝向控件与安卓触屏修复.md` — 触屏事件兼容

### 7.1 数据互发模型

| 方向 | 机制 | 典型内容 |
|------|------|----------|
| 安卓 → 机器人 | WS publish | `/web_goal_pose`、`/remote_cmd_vel`、`/initialpose`、`/navigation_mode`、`/auto_charge_command` |
| 安卓 → 机器人 | WS service call | `/mapping_service/*`（启导航、存地图、开关跟随…） |
| 机器人 → 安卓 | WS subscribe | `/map`、`/tf`、状态码、电量、安全、终态、定位 |
| 安卓 → 机器人 | HTTPS POST（手势场景） | `/api/cmd_vel` |
| 机器人 → 安卓 | HTTP GET | `:9010` 日志（可选） |
| OTA/产线 | MQTT（身份文件） | 远程部署，**不走导航实时路径** |

### 7.2 QoS 注意（安卓/Web 最常见踩坑）

部分状态话题使用 **RELIABLE + TRANSIENT_LOCAL**（类似 latched），订阅端 QoS 不一致可能导致永远收不到：

- `/navigation_mode`
- `/navigation_final_result`
- `/localization_status`（文档明确要求）
- `/safety_status` 等状态类（实现侧常有 durable 语义）

### 7.3 导航为何用 `/web_goal_pose` 而不是 `/goal_pose`

`/goal_pose` 易与 Nav2 `bt_navigator` **双触发**；业务统一：

```
UI → /web_goal_pose → web_goal_pose_bridge → navigate_to_pose action
                    ↘ debounce_handle（监听同目标，处理 ABORT）
```

## 8. 服务回执要做到哪里（分层 ACK）

这是联调“按钮点了但不知道成功与否”的核心。回执是 **分层的**，不是单一字段。

### 8.1 第一层：ROS Service 同步回执（操作开关类）

所有 `/mapping_service/*` 服务响应至少含：

```
bool success
string message
```

附加字段按服务不同：

| 服务 | 额外响应 | 含义 |
|------|----------|------|
| `StartNavigation` | `active_map_name` | 实际加载地图 |
| `MapManagement` | `map_list` / `map_data` / 分辨率尺寸 | 地图 CRUD / 拉取 |
| `WaypointManagement` | waypoints / names | 航点 CRUD |
| `StartAutonomousMapping` | `state` 0–6, map_name… | 自主建图阶段 |
| `StartFallDown` | `is_fallen` | 即时跌倒标志 |
| `SetRunMode` | `production_mode` | 量产/开发者 |

**回执边界**：表示“门闸接受/拒绝启停命令”，**不保证**之后 10 分钟导航必达。

### 8.2 第二层：过程状态（导航执行中）

| 话题 | 类型 | 码表 |
|------|------|------|
| `/navigation_status_code` | `std_msgs/Int32` | 0 UNKNOWN，1 ACCEPTED，2 EXECUTING，3 CANCELING，**4 SUCCEEDED**，5 CANCELED，**6 ABORTED** |
| `/robot_task_status` | `UInt8` | **0 空闲，1 导航中，2 建图中，3 身体跟随** |
| `/localization_status` | `Int8` | 0 正常，1 未就绪，2 异常，3 需关注（含闩锁逻辑） |
| `/mapping_service/status` | 业务字符串状态 | UI 文案 |
| `/safety_status` | `Bool` | true=前方安全可控，false=障碍介入 |
| `/obstacle_status` | `String` JSON | 障碍细节 |
| `/motion_status` | MotionStatus | 点动过程 |
| `/emergency_stop` | `Bool` | true=底盘急停按下/失能 |

发布过程码的节点：`navigation_status_publisher`（autopatrol_robot）。

### 8.3 第三层：导航业务终态（Web/安卓状态栏应以它为准）

**话题**：`/navigation_final_result`  
**类型**：`ox_robot_msg/NavigationFinalResult`

```
int32 code   # 0=SUCCESS 1=FAILURE 2=RETRYING 3=UNKNOWN 4=NAVIGATING
uint32 seq   # 单调序号；约 1Hz 心跳，code 不变也更新 seq，保证 WS 必达流
```

发布方：`debounce_handle`（`patrol_debounce_handle`）。

逻辑要点：

- 监听 `/navigation_status_code`、`/web_goal_pose`、`/navigation_mode`、`/cmd_vel`；
- Nav2 **ABORT(6)** 时：停稳 → 收敛 → 延迟 → **直接 action 重试**（故意不绕 `/web_goal_pose`，避免 bridge 取消旧 goal）；
- 重试耗尽发 **FAILURE(1)**，并 `_gave_up` 防无限重试打爆 CPU；
- 接近目标 Y 向偏差可做 **yaw_correct** 中间点；
- mode=-1 取消时与 status 终态对齐，避免 final=UNKNOWN 与 status=EXECUTING 打架。

**网页实现**：`web/navigation_map.js` 以 final result + status_code 驱动状态栏与多点推进。

**mapping_service 自身**订阅 final result 心跳，用于 `robot_task_status==1`（导航中）判定：Nav2 已起且 debounce 仍在发新鲜 final。

### 8.4 第四层：硬件/感知侧

| 事件 | 通道 |
|------|------|
| 急停 | `/emergency_stop` |
| 充电红外红旗 | `/robot_red_flag` |
| 电量 | `/battery_status` |
| 回充失败原因 | `/recharge_fail_reason` 等 |
| 跌倒 | `/falldown_status` |
| 声源结果 | `/sound_direction_result` |

### 8.5 联调建议（回执“做到哪”的统一语义）

| 操作类型 | 应用应以何为“完成” |
|----------|---------------------|
| 开导航/建图/跟随 | service `success==true` + `robot_task_status` 切到对应模式 |
| 保存地图 | MapManagement success |
| 下发单点导航 | 收到 final `code==0`（或失败 1）；过程中 4=NAVIGATING / 2=RETRYING |
| 急停 | emergency_stop 与 cmd_vel 是否归零 |
| 遥控 | 观测 `/cmd_vel` 与 `/safety_status`，不要只信 POST 返回 |

## 12. 看门狗与「插针」逻辑（软件）

### 12.1 设计目标

边端 CPU 紧，**禁止**每个检测周期 `ros2 topic` / 新建 rclpy participant。改为：

```
topic_health_monitor（ROS 常驻节点）
    每 0.5s 写文件 log/topic_health_status
        ↓
stability_watchdog.sh 每 15s 读文件
    连续 MAX_MISSES（默认 3）后告警
    可选 AUTO_RECOVER=1 + RECOVER_CMD 自动恢复
```

监控通道语义：

| 键 | 含义 |
|----|------|
| `scan: alive/dead` | `/scan` 是否新鲜 |
| `safety_status: alive/dead` | 安全节点是否在发 |
| `ultrasonic_any: alive/dead` | 超声任一路存活 |
| `monitor_ok` | 监控器自身健康 |
| 文件 mtime | 超过 STATUS_MAX_AGE_SEC 视为 monitor 僵死 |

### 12.3 其它“watchdog”字样

## 13. CPU 负载控制（一代必须保留到二代）

| 手段 | 实现 | 为何有效 |
|------|------|----------|
| Foxglove 话题/服务白名单 | launch 参数 | 避免全图序列化 |
| 视觉 Domain 分离 | 34/35 + 最小 bridge | 隔离高带宽 AI 与主业务 |
| 视觉降帧 / 关推流 | `VISION_USB_FPS` 10–12；codec/websocket 默认谨慎 | BPU/带宽省 |
| 跌倒可关 | `START_FALL_DETECTION=0` | 运维降压开关 |
| topic_health 常驻写文件 | 替代周期新建 DDS | 避免探针自噬 |
| 单线程/少空转 | web_goal_pose_bridge 等注释 | 降 scheduler 噪声 |
| 禁 loaned messages | `ROS_DISABLE_LOANED_MESSAGES=1` | 兼容与稳定 |
| UDPv4 only | `FASTDDS_BUILTIN_TRANSPORTS` | 减少 SHM 锁冲突 |
| debounce 有限重试 + gave_up | 防 ABORT 风暴 | 避免失败时 CPU 尖刺 |
| joint_state 低频 | 注释 5Hz | 降 TF 相关 |
| cpu_monitor 自身 nice 19 | 监控不抢业务核 | 只观测 |

**没有** cpulimit / 固定 cgroup 配额作为主手段——二代若引入 cgroup，应作为**加强层**，不能替代上述“少产生负载”的设计。

## 15. 一代架构问题诊断（为何“改一点影响一片”）

### 15.1 实际是单体“星型中枢”

- **`mapping_service_node.cpp` 体量极大**：模式开关、进程生命周期、地图文件、任务互斥耦合在一个 Lifecycle 节点。  
- 改服务字段 / 任务互斥 → 影响 Web、安卓、systemd、文档、白名单。  
- 功能往往 **nohup + pgrep 进程判断**，不是纯 ROS lifecycle，难测、难回滚。

### 15.2 控制面与显示面未 API 化

- 真实 API = “任意 ROS topic/service + 白名单配置文件”。  
- 新增一个字段要改：**msg、C++、JS schema、foxglove 白名单、安卓联调文档** 至少五处。

### 15.3 状态码分裂

导航同时有：action 状态、`navigation_status_code`、`navigation_final_result`、`robot_task_status`。  
历史原因（防抖、多点、WS 丢包）合理，但对新人/二代协议成本高。

### 15.4 速度入口历史分叉

`remote_cmd_vel` 与 `remote_cmd_vel_*` 并存，laser_safety 收口——好在有总出口，但仍增加理解成本。

### 15.5 领域边界模糊

`self_patrol`、`mapping_service`、`debounce_handle` 都染导航语义；视觉包与 domain_bridge 运维脚本耦合深。

### 15.6 配置分散

`/etc/robot-identity`、`ros_env.conf`、launch 参数、YAML、HTML 硬编码路径（home/sunrise）混用。

## 16. 二代架构建议（讨论草案，非冻结方案）

> 目标：保持/加强 **CPU 克制**；消除 **改一处震全局**；给安卓/Web 清晰契约。

### 16.1 分层目标架构

```
┌──────────────────────────────────────────────────────────┐
│ Application Clients: Android / Web / 调试台 / OTA 管理    │
└────────────────────────────┬─────────────────────────────┘
                             │ 唯一契约层（见下）
┌────────────────────────────▼─────────────────────────────┐
│ Robot Control API Gateway                                  │
│  - 强类型版本化：gRPC / JSON-RPC over WS / 或裁剪后 Foxglove │
│  - 统一 RequestId + CommandAck + EventStream               │
│  - 鉴权 / 限流 / QoS 映射                                   │
└──────────────┬─────────────────────────────┬──────────────┘
               │                             │
┌──────────────▼──────────────┐  ┌───────────▼──────────────┐
│ Capability Managers（按模式） │  │ Telemetry Hub（只读）     │
│ mapping / nav / follow /    │  │ 地图切片、tf、电量、健康  │
│ sound / fall / charge       │  │ 采样降频、白名单延续       │
│ 互斥状态机 + lifecycle 标准  │  └──────────────────────────┘
└──────────────┬──────────────┘
               │
┌──────────────▼──────────────────────────────────────────┐
│ Safety Motion Stack（不可绕过）                           │
│ sources → Arbiter → laser_safety → cmd_vel → chassis    │
└──────────────┬──────────────────────────────────────────┘
               │
┌──────────────▼──────────────┐  ┌─────────────────────────┐
│ Drivers Domain              │  │ Vision Domain（隔离）     │
│ chassis / lidar / ultra     │  │ camera / AI / 推流可关   │
└─────────────────────────────┘  └─────────────────────────┘
```

### 16.2 契约层：服务回执统一模型（建议）

每个命令：

```text
Command { command_id, capability, action, payload, timeout_ms }
Ack     { command_id, accepted, reject_reason }          # 100ms 级
Progress{ command_id, phase, percent?, detail }          # 可选
Result  { command_id, ok, code, message, data }          # 终态唯一
Event   { type, severity, body }                         # 急停/掉定位/障碍
```

映射到一代：

| 一代 | 二代 |
|------|------|
| service success/message | `Ack` + 轻量 `Result` |
| navigation_status_code | `Progress.phase` |
| navigation_final_result | **唯一** `Result`（导航能力） |
| robot_task_status | Capability FSM 全局视图的只读投影 |

**原则**：应用只依赖 `Ack/Progress/Result/Event`，不再各自解读五套 topic。

### 16.3 话题精简策略（建议分类）

| 策略 | 做法 |
|------|------|
| **保留** | `/scan`、`/odom`、`/cmd_vel`、`/tf`、`/map`、`/emergency_stop`、`/safety_status` |
| **合并** | 所有电量/充电 → 一个 `robot_power_state`；所有导航过程 → `nav_progress` + `nav_result` |
| **内化** | remote_cmd_vel_* 仅进程内 topic，不暴露 WS |
| **删除候选** | 旧 PowerVoltage（在确认无消费者后）、重复的 status 字符串 |
| **必须双发理由写文档** | map_qos_publisher 若仍需，标 “bridge QoS 适配器”，勿再添同类 |

白名单继续：Gateway 订阅内网全量、对外只 mirror 子集（保留一代 CPU 优点）。

### 16.4 拆 mapping_service 巨石

建议拆为小 manager（同一二进制也可，但 **接口隔离**）：

- `map_store`：文件系统与 GET/UPDATE  
- `slam_session`：slam_toolbox / cartographer 生命周期  
- `nav_session`：加载地图、启 Nav2、初定位健康  
- `feature_session`：follow / fall / sound 互斥令牌  
- `task_arbitrator`：生产模式互斥  

巨型 C++ 文件改为“状态机 + shell/composable 节点标准生命周期”，禁止 pgrep 作为主要状态真相。

### 16.5 安全运动栈前置

二代所有运动源（Nav2、跟随、手势、回充）注册进 **Arbitrator**：

- 优先级：E-stop > 安全制动 > 手动 > 导航 > 跟随  
- 单出口 `/cmd_vel`  
- 保留 laser_safety 区域策略（可参数化 YAML，独立版本）

### 16.6 继续压 CPU（加强一代套路）

1. Gateway 侧按客户端订阅集 **按需开 topic**（比固定白名单更灵活，默认更少）。  
2. 地图：**分级**：全局缩略 + 视口切片，避免网页反复收全图。  
3. 视觉默认 **Warm pool 可选、冷启动可接受时默认冷**；量产配置表明确。  
4. Nav2 参数与 debounce 重试上限配置进入 **capacity profile：eco / normal / demo**。  
5. 可加 cgroup soft limit 给 vision 域，但不要替代“少发”。  

### 16.7 安卓与 Web

- 同一 OpenAPI / protobuf 契约版本 `v1/v2`，兼容期双栈。  
- 二代可不再强绑 ROSLIB API；内网仍可用 ROS bag 调试。  
- 一代 Foxglove 可作为 **DevOps 调试面** 保留，业务主路径走 Gateway。

### 16.8 可观测性

把 topic_health_status、CPU spike、localization、final result 汇总为：

- Prometheus/文本指标 或  
- 本地 `robot_health.json` + HTTP  

看门狗继续：**文件探针低成本路径保留**。
